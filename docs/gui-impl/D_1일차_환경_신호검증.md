## 환경과 실행

확인한 기존 환경: Python 3.12.16, PySide6-Essentials 6.12.0, jsonschema 4.26.0. 모듈 import를 실제 실행해 확인했고 설치는 하지 않았다. GUI 창 표시 확인은 이번 범위에서 하지 않았다.

프로젝트 루트의 PowerShell에서 실행한다.

```powershell
$env:PYTHONPATH = 'src'
& C:/Users/user/anaconda3/envs/eyetoarm/python.exe -B -m eyetoarm.d_client --env-only
& C:/Users/user/anaconda3/envs/eyetoarm/python.exe -B -m eyetoarm.d_client --host 127.0.0.1 --port 47090 --timeout 3 --json
```

진단은 기존 `eyetoarm.tcp.protocol`의 패킷 작성·엄격 STATUS 파서·종류 판정을 재사용한다. 따라서 기존 tcp 폴더를 추후 이동할 때는 이 import 소비자도 함께 검토해야 한다. 같은 규약의 두 번째 구현은 만들지 않는다.

`--host`는 숫자 IPv4/IPv6만 받으며 `localhost` 대신 `127.0.0.1`을 쓴다. DNS가 총 기한 밖에서 지연되는 것을 피하기 위한 1일차 제한이다. `--timeout`은 접속+송신+수신의 총 기한(기본 3초)으로, 운영 클라이언트의 접속/준비 응답 분리 타이머를 대체하지 않는다. `--check-env`는 환경과 접속을 함께 진단하며, 환경 불일치여도 접속 결과를 출력한다.

종료 코드: 0=유효 STATUS 또는 환경만 점검 성공, 1=접속 실패, 2=프로토콜 실패, 4=환경 불일치, 5=잘못된 인자. 환경 불일치가 있으면 최종 코드는 4이고 접속 결과는 출력에 보존한다. 유효 STATUS의 robot_ready=false는 종료 0이며 로봇 준비 여부는 별도 필드다. JSON 출력의 exit_code는 실제 종료 코드와 같다.

## C↔D 신호와 판정

### GUI·대시보드로 이어지는 책임 분리

D의 최종 산출물은 Windows GUI·운영 대시보드다. 사용자가 1일차 코드를 GUI 재사용 기준으로 정리하도록 선택했으며, 이번에는 화면 구현까지 확장하지 않는다.

| 위치 | 책임 | GUI에서의 사용 |
|---|---|---|
| d_client/models.py | ProbeResult 데이터 모델, Qt/소켓/콘솔 진입점과 독립 | 상태 카드가 진단 결과를 소비. dataclasses.asdict(result)로 별도 스냅샷 전달 가능 |
| d_client/diag.py | 환경 점검·동기 단발 접속 진단·결과 문자열/기록 변환 | 사전점검용. probe는 GUI 스레드에서 직접 호출하지 않음 |
| d_client/__main__.py | 명령행 옵션·출력·종료 코드 | 진단 실행 진입점. GUI의 통신/상태 관리자로 사용하지 않음 |
| 기존 tcp/protocol.py | 공통 신호 작성·엄격 STATUS 검증 | 후속 비동기 운영 클라이언트도 동일 계약 재사용 |

diag.ProbeResult 경로도 재수출해 기존 호출과 시험을 보존한다. models.py는 GUI 전체 상태 관리자가 아니라 **1일차 진단 결과 모델**이다. 실제 GUI에서는 하나의 비동기 통신 소유자가 C 연결을 유지하고, 수신 검증 → 공통 상태 → 조작/대시보드/기록 갱신 순서로 연결한다. 탭마다 별도 연결을 만들거나 화면 갱신 중 blocking connect/recv/sleep를 실행하지 않는다. 연결됨·유효 응답 수신·robot_ready는 별도로 표시한다.

후속 화면은 D 상세설계의 조작·설정/운영 대시보드/평가·기록과 GUI-01~04를 따른다. 현재 기존 gui/tcp/pendant는 시험용으로 보존하고 새 Windows 화면을 대체하는 것으로 간주하지 않는다. GUI·비동기 지속 연결·MOVE/분류·영상 중계는 해당 일차에서 구현/검증한다. 이번 정리로 이 기능들이 완성됐다는 뜻은 아니다.

정리 후 검증: socket·PySide6·TCP protocol import를 막은 별도 Python에서 models.ProbeResult를 가져와 스냅샷으로 변환하는 회귀1건을 추가했다. 기존 직접 실행·진단·C 계약 시험과 합계43건이 통과했다. diag.ProbeResult 등 기존 공개 경로와 종료 코드 동작을 유지했다. 상시 서버·GUI·커널은 만들지 않았고 대역 스레드와 시험 전경 프로세스는 종료했다. 실제 C 서버 접속은 이번 정리에서 다시 시험하지 않았다.

직접 파일 실행도 지원한다. 저장소 루트에서 아래 명령은 PYTHONPATH 설정 없이 동작한다. IDE에서 diag.py 또는 __main__.py를 실행해도 같은 CLI로 연결된다. 다른 폴더에서는 파일의 절대 경로를 지정한다. Python은 위 eyetoarm 환경을 선택한다.

```powershell
& C:/Users/user/anaconda3/envs/eyetoarm/python.exe -B src/eyetoarm/d_client/diag.py --env-only
& C:/Users/user/anaconda3/envs/eyetoarm/python.exe -B src/eyetoarm/d_client/__main__.py --env-only
```

2026-11-12 실행 경로 수정: 직접 실행 시 src가 모듈 경로에 없어 발생하던 `ModuleNotFoundError: No module named 'eyetoarm'`을 재현했다. 두 파일은 직접 실행일 때 파일 위치 기준 src 경로를 추가하며, diag.py는 공용 CLI에 위임한다. 패키지 import에는 경로 변경이 없다. 전역 환경·의존성 설치·기존 GUI 코드는 변경하지 않았다. PYTHONPATH 없는 다른 작업 폴더에서 직접 실행, 도움말, 기존 모듈 실행을 확인하는 회귀3건을 추가했고 기존39건과 합계42건을 통과했다. 두 파일의 직접 환경 진단도 각각 exit0을 확인했다. 이 수정에서는 실제 C 서버 접속을 다시 시험하지 않았다.

| 방향/단계 | 내용 | 성공·해석 기준 |
|---|---|---|
| D→C | `{"version":"1.1","type":"GET_STATUS"}` + LF, command_id 없음 | 접속당 한 번만 전송; MOVE/CANCEL/분류 명령 미전송 |
| C→D | UTF-8 JSON STATUS 한 줄, CRLF 허용 | LF 완성 후 엄격 파싱·스키마/일관성 검사. 과대 줄·EOF 조각·잘못된 UTF-8/중복 키/비유한 수 거부 |
| 응답 종류 | 준비 응답 | command_id/state/code 없는 STATUS만 이번 조회의 정상 응답. 거부/명령 알림은 성공으로 오인하지 않음 |
| 접속 | TCP 접속 여부 | 연결 거부·시간 초과·DNS/OS 오류를 프로토콜 판정과 분리 |
| 로봇 준비 | robot_ready, not_ready_reasons, active_command_id | 유효 STATUS의 ready=false도 통신 확인은 성공이며 로봇 동작 준비는 미완료 |
| 시간 | 로컬 단조 시계로 진단 경과 측정 | server_time_ms와 Windows 시계를 직접 빼지 않음 |

C의 `readiness.py`는 현재 준비 false/RECOVERING 스텁이며, `tcp_server.py`는 장면/ROS/로그 상태를 더한다. 실제 응답은 RECOVERY_FAILED 또는 다른 미준비 사유일 수 있다. D가 이를 지우거나 C의 명령 로그를 초기화하지 않는다. 이 도구는 C 서버를 띄우거나 종료하지 않는다.
